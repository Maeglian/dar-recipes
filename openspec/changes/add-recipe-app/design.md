# Design

## Context

Проект начинается с нуля: в репозитории только каркас OpenSpec, кода, сборки и тестов нет. Мотивация — в proposal.md, требования — в `specs/`.

Ограничения, которые определяют подход:
- Сервера нет. Всё хранится в браузере на устройстве, и данные должны переживать перезапуск и работу офлайн.
- Основное устройство — телефон, в том числе iPhone с Safari. От этого зависят хранилище, кодирование картинок и установка.
- Пользователь один и пишет на Vue. Стек выбран в обсуждении: Vue 3 + Vite + TypeScript.

## Goals / Non-Goals

**Goals:**
- Вся логика пересчёта, округления и сборки списка покупок — чистые функции без зависимостей от Vue и IndexedDB, покрытые unit-тестами.
- Только слой репозиториев знает об IndexedDB, чтобы позже можно было заменить хранилище, например на Supabase, не трогая UI.
- UI реактивно отражает изменения в базе, включая изменения из другой вкладки, без ручной синхронизации состояний.

**Non-Goals:**
- Синхронизация, учётные записи, тёмная тема (см. proposal).
- Перетаскивание ингредиентов жестом: порядок меняется кнопками «вверх» и «вниз».
- Поддержка старых браузеров: целимся в актуальные Safari iOS и Chrome.

## Decisions

### 1. Структура проекта
Одно Vite-приложение в корне репозитория рядом с `openspec/`:

```
src/
  domain/        чистая логика: units, scaling, format, shopping-list, validation
  data/          Dexie: db.ts (схема), *Repository.ts, backup.ts (экспорт/импорт)
  composables/   useLiveQuery, useRecipe, useShoppingList, ...
  views/         CatalogView, RecipeView, RecipeEditView, ShoppingListView,
                 CollectionsView, DataView
  components/    RecipeCard, IngredientRow, ServingsStepper, RatingPicker, ...
  styles/        tokens.css (цвета, отступы), base.css
```

Маршруты: `/` (каталог), `/recipes/new`, `/recipes/:id`, `/recipes/:id/edit`, `/shopping`, `/collections`, `/data`. Используется `vue-router` в режиме hash, чтобы статический хостинг работал без настройки fallback-роутинга.

### 2. Хостинг: GitHub Pages
Код живёт в публичном репозитории https://github.com/Maeglian/dar-recipes, и приложение публикуется на `https://maeglian.github.io/dar-recipes/`. На бесплатном аккаунте Pages работает только с публичными репозиториями. Публикуется код, данные пользователя на GitHub не попадают.

- Деплой выполняет workflow GitHub Actions (`.github/workflows/deploy.yml`): при пуше в `main` запускаются `npm ci`, `npm run typecheck`, `npm test` и `npm run build`, а затем `actions/upload-pages-artifact` и `actions/deploy-pages`. В настройках Pages должен быть выбран источник «GitHub Actions».
- Приложение работает в подпапке `/dar-recipes/`, а не в корне домена. В Vite задаётся `base: './'`, в манифесте PWA — `start_url: './'` и `scope: './'`. Тогда сборка не зависит от имени репозитория, а service worker регистрируется в рамках подпапки.
- Hash-роутинг (решение 1) нужен, потому что Pages не умеет отдавать `index.html` вместо 404 для произвольных путей.
- Данные IndexedDB привязаны к origin `maeglian.github.io`, а не к пути. Их делят все Pages-проекты этого аккаунта, поэтому база называется уникально — `dar-recipes`. Переименование репозитория данные не теряет, а смена логина на GitHub теряет: адрес изменится, и данные придётся переносить через экспорт и импорт.
- В удалённом репозитории уже есть первый коммит с README. Поэтому локальная история начинается с `git pull` этого коммита, а не с собственного первого коммита.

### 3. Хранилище: Dexie поверх IndexedDB
Голый IndexedDB слишком многословен, а localStorage синхронный, ограничен примерно 5 МБ и не хранит Blob. Dexie даёт удобные запросы, версии схемы и `liveQuery`.

Схема (версия 1, база `dar-recipes`):

| Таблица | Ключ и индексы | Содержимое |
|---|---|---|
| `recipes` | `id, titleKey, *collectionIds` | рецепт целиком, ингредиенты вложены массивом |
| `images` | `id` | `{ id, blob }`; id совпадает с id рецепта |
| `collections` | `id, &nameKey` | `{ id, name, nameKey }` |
| `manualItems` | `id, createdAt` | пункт, добавленный вручную |

- **Ингредиенты вложены в рецепт** и имеют стабильный `id` (`crypto.randomUUID()`). Отдельная таблица не нужна: ингредиенты не живут без рецепта. А по стабильному id список покупок ссылается на источник при отметке, и отметки переживают редактирование рецепта.
- **Картинки — в отдельной таблице.** Иначе каждый запрос каталога и каждая `liveQuery` по рецептам тащили бы мегабайты Blob'ов.
- **`selected`, `rating` и `bought` не индексируются.** Boolean не может быть ключом IndexedDB, а рецептов — сотни, не миллионы. Фильтрация идёт в памяти.
- `titleKey` и `nameKey` — нормализованные строки (lowercase, trim). Уникальный индекс `&nameKey` обеспечивает уникальность названий коллекций на уровне базы.

Модель (TypeScript):

```ts
type UnitKey = 'g' | 'kg' | 'ml' | 'l' | 'pcs' | 'tsp' | 'tbsp' | 'cup' | 'custom'
type Rating = 'excellent' | 'good' | 'sometimes' | 'bad'

interface Ingredient { id: string; name: string; amount: number | null;
  unit: UnitKey | null; customUnit: string | null; bought: boolean }
interface Recipe { id: string; title: string; titleKey: string; description: string;
  hasImage: boolean; baseServings: number; servings: number; rating: Rating | null;
  collectionIds: string[]; selected: boolean; cooked: boolean; ingredients: Ingredient[];
  createdAt: number; updatedAt: number }
interface Collection { id: string; name: string; nameKey: string }
interface ManualItem { id: string; name: string; amount: number | null;
  unit: UnitKey | null; customUnit: string | null; bought: boolean; createdAt: number }
```

Если `amount === null`, то `unit === null`: это ингредиент «по вкусу».

### 4. Слой репозиториев и реактивность
Только `src/data/*Repository.ts` импортируют Dexie. Их методы описывают операции предметной области (`setServings`, `toggleBought(recipeId, ingredientIds[], value)`, `resetBought`, `deleteCollection`, ...), а не CRUD таблиц. Многошаговые операции выполняются в одной транзакции: удаление коллекции вместе с её снятием со всех рецептов, отметка строки списка покупок, затрагивающей несколько рецептов и ручных пунктов.

Чтение идёт через composable `useLiveQuery(fn)`. Он подписывается на `liveQuery` Dexie и кладёт результат в `shallowRef`, отписка происходит в `onScopeDispose`. Pinia не нужна: источник истины — база, а `liveQuery` сам перечитывает данные при изменениях, в том числе из другой вкладки.

Альтернатива — Pinia со стором в памяти и записью в базу. Отвергнута, потому что появляются два источника истины и ручная синхронизация.

### 5. Единицы, пересчёт и форматирование
`src/domain/units.ts` описывает для каждой единицы семейство и множитель к базовой единице семейства:

| Семейство | Единицы (множитель) | Шаг округления (в базовой) | Формат |
|---|---|---|---|
| `mass` | g (1), kg (1000) | 1 г | < 1000 → «N г», иначе «N,NN кг» |
| `volume` | ml (1), l (1000) | 1 мл | < 1000 → «N мл», иначе «N,NN л» |
| `pcs` | pcs (1) | 0.5 | «4,5 шт» |
| `tsp` / `tbsp` / `cup` | каждая отдельно (1) | 0.25 | «1½ ст.л.», «¾ ч.л.» |
| `custom:<ключ>` | custom (1) | нет | до 2 знаков после запятой |

Ложки и стаканы — разные семейства. Переводить ст.л. в ч.л. мы не договаривались, и это отдельное решение.

`scale(amount, base, servings)` возвращает `amount * servings / base`. `roundTo(x, step)` вычисляет `Math.max(step, Math.round(x / step + 1e-9) * step)`: эпсилон защищает от ошибок вида `0.49999…`, а максимум не даёт ненулевому количеству превратиться в ноль. Округление выполняется только при отображении. В базе хранится введённое количество, поэтому ошибки не накапливаются (см. сценарий «Возврат к исходным порциям»).

Числа форматируются через `Intl.NumberFormat('ru-RU', { maximumFractionDigits: 2 })`, это даёт запятую и отбрасывает лишние нули. Четверти отображаются символами `¼ ½ ¾`.

### 6. Сборка списка покупок
`buildShoppingList(recipes, manualItems)` — чистая функция:

1. Берёт ингредиенты из `selected` рецептов с количеством, пересчитанным по `servings` рецепта и переведённым в базовую единицу. Ручные пункты берутся без пересчёта.
2. Группирует по ключу `normalize(name) | family | bought`. `normalize` переводит в нижний регистр, убирает пробелы по краям и схлопывает повторные пробелы. Для `custom` семейство включает нормализованное название единицы. Пункты без количества образуют семейство `none`.
3. В группе суммирует количества в базовой единице и округляет сумму один раз по правилам семейства.
4. Строка хранит список источников `{ kind: 'recipe', recipeId, ingredientId } | { kind: 'manual', id }`, подпись (названия рецептов по алфавиту и «вручную» в конце) и отображаемое название — исходное написание первого источника.
5. Сортирует строки: сначала некупленные, потом купленные, внутри — `localeCompare(…, 'ru')`.

Поскольку `bought` входит в ключ группы, частично купленный продукт естественно распадается на две строки, как того требует спека. Отметка строки — это одна транзакция `setBought(sources, value)`.

### 7. Картинки
Картинка обрабатывается на клиенте: `createImageBitmap(file)` (ориентация EXIF учитывается браузером), затем canvas с длинной стороной не больше 1200 px, затем `canvas.toBlob('image/jpeg', 0.85)`. Выбран JPEG, а не WebP: кодирование WebP через canvas в Safari ненадёжно, а для фото еды разница в размере некритична. Ошибка декодирования превращается в сообщение пользователю, текущая картинка при этом не трогается.

Для отображения используется `URL.createObjectURL(blob)`, а при размонтировании компонента — `revokeObjectURL`. В каталоге показывается та же картинка, обрезанная через `object-fit: cover`. Миниатюры отдельно не храним: при 1200 px и JPEG 0.85 это примерно 150–300 КБ на рецепт, для сотен рецептов приемлемо.

Поле ввода — `<input type="file" accept="image/*">`. На телефоне оно само предлагает выбор между камерой и галереей.

### 8. Экспорт и импорт
Формат файла:

```json
{ "app": "recipes", "version": 1, "exportedAt": "2026-10-16T12:00:00Z",
  "recipes": [...], "collections": [...], "manualItems": [...],
  "images": [{ "id": "...", "type": "image/jpeg", "data": "<base64>" }] }
```

- При экспорте Blob'ы переводятся в base64 через `FileReader`, файл отдаётся через `Blob` и `<a download>`.
- Импорт проходит в два этапа. Сначала файл полностью разбирается и проверяется (поле `app`, поддерживаемая `version`, обязательные поля и типы, ссылки на коллекции), base64 декодируется. Только потом в одной транзакции Dexie выполняется `clear()` всех таблиц и `bulkAdd`. Если что-то падает до транзакции или внутри неё, текущие данные остаются нетронутыми: транзакция откатывается.
- `version` позволит в будущем мигрировать старые файлы, а также перенести данные на бэкенд.

### 9. PWA и постоянное хранилище
`vite-plugin-pwa` с `registerType: 'autoUpdate'` и стратегией `generateSW` прекэширует всю сборку. Манифест содержит название, `display: standalone`, относительные `start_url` и `scope` (см. решение 2), `theme_color` и иконки 192 и 512 px (плюс maskable и `apple-touch-icon` для iOS).

При старте вызывается `navigator.storage.persist()`, результат кладётся в реактивное состояние, а экран «Данные» показывает предупреждение, если `persisted() === false` или API недоступен.

### 10. Цвета оценок
Цвета задаются CSS-переменными в `tokens.css`. Все они пастельные, а основной текст `#1f2328` даёт на каждом из них контраст выше 4.5:1.

| Оценка | Фон |
|---|---|
| Отлично | `#dcf5e3` |
| Хорошо | `#dcedfb` |
| Иногда можно попробовать | `#fff4c2` |
| Плохо | `#fde0de` |

UI-библиотеки нет, только свой CSS mobile-first. Компонентов немного, а библиотека добавила бы вес и чужую стилистику.

### 11. Тестирование
- `vitest` для `src/domain` (пересчёт, округление, форматирование, сборка списка, валидация). Сценарии из спеков переносятся в тесты почти дословно.
- `fake-indexeddb` для репозиториев и экспорта/импорта: транзакционность, удаление коллекции, атомарность импорта.
- `@vue/test-utils` в окружении `happy-dom` для ключевых компонентов: шаговый переключатель порций, строка ингредиента, форма рецепта.
- Сжатие картинок, установка PWA и офлайн-режим проверяются вручную в браузере и на телефоне, так как canvas и service worker в jsdom/happy-dom не воспроизводятся.

### 12. «Новое» и «Приготовлено»
«Новое» — не запись в таблице `collections`, а вычисляемая коллекция: все рецепты с `cooked === false`. Альтернатива — настоящая коллекция, которую приложение ставит и снимает само — отвергнута: её можно переименовать, удалить или снять вручную, и тогда она разошлась бы с отметкой «Приготовлено». Пришлось бы защищать её особыми случаями во всём коде коллекций.

- В `Recipe` добавляется `cooked: boolean`. Схема Dexie поднимается до версии 2 с `upgrade`, который проставляет `cooked = rating !== null`: оценка означает, что рецепт готовили (решение «оценка отмечает приготовленным»), а остальные рецепты попадают в «Новое». Поле не индексируется, как и другие булевы (решение 3).
- `createRecipe` создаёт рецепт с `cooked = false`. `updateRecipe` поле не трогает. `setRating` с непустой оценкой ставит `cooked = true` в той же операции. Снятие оценки отметку не меняет.
- В фильтре каталога «Новое» кодируется зарезервированным значением `collection=new` в адресе. id настоящих коллекций — UUID, поэтому совпадение исключено. Константа `NEW_COLLECTION_ID` живёт в `src/domain/catalog.ts`.
- Формат экспорта поднимается до версии 2 с полем `cooked`. Импорт принимает версии 1 и 2, у файлов версии 1 `cooked` выводится так же, как при миграции.

### 13. Диагностика зависаний
На телефоне наблюдалось зависание «Загрузки…» почти на минуту после постановки оценки. В эмуляции оно не воспроизвелось, а консоли телефона нет. Поэтому приложение само показывает своё состояние: middleware Dexie на уровне `dbcore` учитывает каждую транзакцию (режим, таблицы, время начала) и снимает её по `complete`, `abort` или `error`. Кроме того, учитываются события `ready`, `blocked` и `versionchange`. Компонент `LoadingState` заменяет «Загрузка…» во всех экранах и через 5 секунд показывает эти данные. Обработчик дешёвый: он лишь добавляет запись в массив и снимает её, так что остаётся включённым постоянно.

Альтернатива — удалённый сбор логов. Отвергнута: нужен сервер, которого у приложения нет и не будет (см. proposal).



- [Safari очищает хранилище неустановленных сайтов, которые не открывали примерно 7 дней] → запрос `storage.persist()`, предупреждение на экране «Данные», рекомендация установить приложение, экспорт в файл.
- [Квота хранилища и рост числа картинок] → сжатие до 1200 px и JPEG; рост около 0,3 МБ на рецепт. Ошибку `QuotaExceededError` при сохранении нужно поймать и показать понятным сообщением.
- [Файл экспорта примерно на треть больше данных из-за base64] → приемлемо для личного объёма. При необходимости позже можно перейти на zip.
- [Ошибки округления чисел с плавающей точкой] → округление только при отображении, эпсилон в `roundTo`, сценарии из спеков в тестах.
- [Сложение по точному названию не объединит «мука» и «мука пшеничная»] → осознанное ограничение (см. proposal), источники видны под строкой.
- [Данные привязаны к адресу `maeglian.github.io`: смена логина на GitHub или переезд на другой хостинг откроют приложение пустым] → перед такой сменой сделать экспорт и затем импорт на новом адресе.
- [Импорт полностью заменяет данные] → обязательное подтверждение, предварительная валидация, одна транзакция.
- [Купленные ингредиенты выбранных рецептов не убираются кнопкой «Очистить купленное»] → поведение согласовано. Пользователь снимает выбор с рецепта, и они уходят из списка.

## Migration Plan

Мигрировать нечего, это первая версия. Изменения схемы в будущем — через `db.version(n).upgrade(...)` в Dexie. Изменения формата экспорта — через поле `version` с конвертером старых версий при импорте.

## Open Questions

- Название и иконка приложения. В задачах используются временные; заменить их можно в любой момент.
- Стоит ли «Очистить купленное» заодно снимать выбор с рецептов, где куплено всё? Это дополнение к согласованному поведению, его можно добавить позже, не ломая остального.
